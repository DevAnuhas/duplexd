# Practice Sandbox server protocol

Status: paired server/runtime protocol deployed for configured Practice calls. Real preview calls have demonstrated audible two-way voice and bounded hidden-tab continuity; the integrated [A07 Stage A acceptance](https://github.com/DevAnuhas/duplexd/issues/66) remains open. [ADR 014](../decisions/014-gated-sandbox-protocol.md) records the staged protocol and [ADR 015](../decisions/015-server-configured-sandbox-execution.md) supersedes its disabled-admission decision.

## Ownership and source

The typed contract is [sandbox/protocol.ts](../../apps/workspace/src/sandbox/protocol.ts); [sandbox/lifecycle.ts](../../apps/workspace/src/sandbox/lifecycle.ts) owns transactions, owner checks and reconciliation. The narrow [execution authority](../../apps/workspace/src/sandbox/execution.ts) shares row locking and durable deadline decisions between lifecycle operations and signed Practice selection/release. [provider.ts](../../apps/workspace/src/sandbox/provider.ts) is the only composition layer that reads the five provider settings and constructs the live transport and browser-media verifier. The settings are all-or-nothing: without them start, join and presence return `503 sandbox_execution_disabled`; with them the routes can dispatch. No browser input enables execution. Prepare/expiry/cancel retain their session, Origin, CSRF and controller-proof contract.

An attempt row lock serializes dispatch, registration, claim, stop and result reconciliation. Dispatch commits `dispatching`, the token hash and absolute deadlines before one transport request; raw token exists only in the unchanged runner body `{callId, apiBase, agentToken}`. A duplicate start never remints or resends. Process loss between commit and request is unknown, not permission to retry.

## Runtime ownership and control

Every new-protocol request sends `Authorization: Bearer <call token>` and `x-duplexd-protocol: sandbox-v1`. Session and boot IDs are opaque strings of 1–128 ASCII letters, digits, `_` or `-`.

| Request                             | Additional input                            | Success response                                          |
| ----------------------------------- | ------------------------------------------- | --------------------------------------------------------- |
| `POST /v1/agent/calls/:id/register` | JSON `{sessionId, bootId}`, maximum 4 KiB   | `{protocol: "sandbox-v1", registered: true}`              |
| `GET /v1/agent/calls/:id/config`    | `x-duplexd-session-id`, `x-duplexd-boot-id` | `{protocol, owner: {sessionId, bootId}, config, control}` |
| `GET /v1/agent/calls/:id/control`   | Same owner headers                          | `{protocol, control}`                                     |

Protocol and registered owner cannot be replaced. Same-owner registration is idempotent while execution is valid. Conflicting identity stops execution and preserves observed session references for exact cleanup, including further authenticated identities received after the first conflict while reporting remains permitted. Every retained reference must independently become terminal before capacity is released. An authenticated late registration may reveal the lost start's exact target, but cannot claim configuration or reconstruct a missing join token. Registration after confirmed cleanup or the reporting deadline is refused.

`config` has the existing camelCase runtime configuration keys. It uses the frozen Practice snapshot, a new per-call encrypted Practice secret and internal `/v1/practice/calls/:id/tools` URL; no customer endpoint or webhook secret is read. Owner, stop intent and deadlines are checked before minting/returning plaintext. Claim is atomic and one-time: retry returns 409, never plaintext. Claim is not readiness. Authenticated evidence ingestion updates readiness under the same lifecycle lock, only while execution remains valid.

`control` contains `stopRequested`, `stopReason`, `startupDeadline`, `executionDeadline`, `presenceExpiresAt`, `serverTime`, `pollIntervalMs`, `controlLossTimeoutMs`, `gracefulStopMs` and `reportingGraceMs`. Dates are ISO strings. Poll interval is 3 seconds; control loss stops execution after 30 seconds; graceful stop allows 10 seconds; reporting-only grace is 60 seconds. Polling does not extend startup, execution or browser presence. A late request applies the original earliest due deadline rather than starting a fresh grace period.

Legacy Integration requests retain their exact config, ACK and completion shapes. Legacy config/events/completion reject Sandbox credentials before mutation. Versioned completion is the only Sandbox path that writes `ended`, based on the original runtime owner's observed reason and measured duration. Unclaimed termination is `failed`; claimed termination without authenticated completion is `incomplete`. A bounded late completion can correct that record, retains the original reporting deadline and adds a platform reconciliation event. Neither completion nor telemetry releases unresolved private resources.

## A04 evidence wire contract

The following contract is shared by the deployed runtime and server; the contract alone is not acceptance evidence. `GET /v1/agent/calls/:id/protocol` authenticates the call token without claiming configuration and returns `{protocol: "sandbox-v1"}` or `{protocol: "integration-v1"}`. The runner body remains exactly `{callId, apiBase, agentToken}`. Sandbox uses the runner's exact session ID and a per-process boot ID for registration before its single configuration claim. A runtime talking to an older server may use the legacy Integration path only when negotiation is absent (404), never after a Sandbox negotiation or registration failure.

Versioned `POST events` requires the owner headers and `{events: [{seq, at, type, payload}]}`. `agent_ready` is the additional readiness marker, emitted once after the three actual barriers; its payload is empty. Existing event names retain their meaning. No raw tool arguments, results, secrets or reasoning traces are exposed by polling. ACKs are `{protocol, contiguousSeq, missingRanges, evidenceState, completionDigest, control}`. Missing ranges are inclusive sequence pairs, capped at 32; retransmission of identical canonical content is accepted, conflicting sequence content is persisted as an integrity failure. Events are limited to 8 KiB, batches to 64 events / 256 KiB, pending runtime delivery to 1,000 events / 2 MiB, and the call to 10,000 events / 8 MiB. Control polling is independent of evidence delivery.

Versioned completion requires exactly `{endedReason, durationSecs, finalSeq, producerLoss, truncated}`. The server computes a canonical completion digest and returns it in the ACK; identical retries acknowledge the existing completion, conflicts never replace it. `finalSeq` seals the agent namespace. Platform observations have a separate namespace and do not affect the final watermark. Reporting grace admits missing historical events through that watermark, including late readiness, without renewing execution or making a stopped attempt active. Evidence is `unknown` before a seal, `partial` for gaps/loss/truncation/conflicts, and `complete` only when every emitted sequence through the seal is accounted for without those flags. This is delivery completeness, not proof of all spoken audio or model correctness.

The live and historical timelines consume authenticated, account-scoped `GET /api/workspace/sandbox/calls/:id/events?after=<cursor>` and safe call projections. The typed `SandboxEventPage` contains `events`, `nextCursor`, `hasMore` and an `evidence` summary. Each safe event carries an opaque ingestion cursor, `namespace`, producer `seq`, `at`, `type` and allowlisted `payload`. The cursor orders ingestion rather than producer sequence, so a late sequence 7 remains visible after sequence 8. A cursor is never authorization. Pages are bounded to 100 events / 128 KiB. Transcripts are user content and can contain sensitive spoken text; neither polling nor logs promise PII-free text. The UI may display explicit loss or reconciliation but must not treat absence of telemetry as a clean ending.

## Runtime shutdown and evidence ownership

The Python client negotiates without changing the legacy runner body, registers the runner session plus one boot identity, then claims once. Negotiation/registration/claim share a 20-second local startup bound. Once claimed, independent control and monotonic-watchdog tasks start before the Responses capability probe. Absolute server deadlines are conservatively anchored to request-start monotonic time; delayed control cannot revive an expired lease or extend startup/execution. Tool admission consults the watchdog before dispatch and never retries an unknown-effect webhook.

After the backend probe succeeds, Daily's `on_connected` and OpenAI Live's `on_session_started` jointly release the one-shot readiness marker. The first browser `on_client_connected` queues the initial `LLMRunFrame`; duplicate participant callbacks cannot repeat the greeting. SDK websocket setup is not treated as a started voice session, and neither transport readiness nor telemetry proves audible browser playback.

The bounded queue retains immutable event content until a valid contiguous ACK; a lost response resends the same bytes. Overflow or an oversized event records producer loss (and truncation when oversized) and requests shutdown through the independent watchdog, never by cancelling from inside the reporter task. The pipeline and its child backend worker stop before the reporter seals its final watermark. Reporting drains for at most 15 seconds after costly work stops; measured duration excludes that drain. An unobserved process exit produces no synthetic clean completion. The complete live fault matrix is still unverified under A07.

Pipecat 1.11.0 can unwind `WorkerRunner.run()` during startup before reaching its cleanup guard. Its public `cancel()` only signals that loop; a finished supervisor is therefore not proof of stopped media. Sandbox teardown explicitly awaits the pinned `_cancel_spawned_workers()` primitive (including child-worker joins), public runner cleanup and bus shutdown, and checks for remaining live owned tasks. The runner-stopped marker and backend-client closure must both be confirmed before sealing. Cleanup failure, interruption or the ten-second shutdown bound leaves completion unsealed and the server to record incomplete state. This is a narrow private-SDK dependency, not a fork: retain the real-runner startup-yield regression when upgrading Pipecat, and remove the hook only when a public awaited teardown covers partial startup.

The additive `sandbox_evidence` ledger and nullable `call_events` ingestion/digest/byte columns leave legacy records unchanged. The attempt/call lock serializes the ledger, duplicate checks, readiness and completion. A persisted integrity flag cannot be erased by a later retry. Malformed authenticated evidence is separately limited to ten errors per minute; empty evidence heartbeats are limited to one per three seconds. Valid replay and control polling do not consume those limits. Event payload nesting is bounded to sixteen levels. Safe tool projections can include `practiceScenario` and `practiceSelectedStatus` from the server's signed invocation selection; these mean the synthetic response selected by Practice, not proof it reached the model or a generic interpretation of business success.

## Browser and deadlines

Prepare/current/status include `execution: "enabled"` only when the same server configuration predicate used by start/join/presence is satisfied; otherwise they report `"disabled"`. They also include `resourceState`, nullable `startupDeadline`, `executionDeadline`, `presenceExpiresAt`, persisted `readyAt` and `serverTime`; no owner proof, provider ID, snapshot or credential is projected. Status is account-scoped. Join/presence require the initiating user and original tab proof. Stop requires the initiating session but not the lost tab proof.

[browser-contract.ts](../../apps/workspace/src/sandbox/browser-contract.ts) freezes browser response types: start/stop `{attempt}`, join `{join}`, presence `{presenceExpiresAt, serverTime}`. The `enabled` alternative reflects server configuration, not a browser admission switch. The client combines persisted readiness with local capture/output/join and current leases; after a ready call returns from a hidden tab, it waits for a fresh presence response before showing Connected. Historical readiness alone cannot revive execution. Resource release requires `confirmed_stopped`, or canceled/expired preparation with `not_dispatched` resources; a terminal call alone is insufficient.

Join output is `{sessionId, dailyRoom, dailyToken, expiresAt}`, only for the controller while unexpired and non-stopping, never from status/current. Its encrypted envelope binds the credential to attempt and call. The provider start requests a browser participant token and bounds its lifetime by the execution deadline. The returned token's effective room/role scope is not independently proved by the published response contract; the verifier enforces expiry, not scope.

Preparation expires after 30 seconds. Startup is bounded by 120 seconds, execution by 600 seconds from dispatch, and presence by a renewable 60-second lease. Presence never extends execution or resurrects an attempt. Stop advances overdue deadlines before recording user intent, so a late click cannot renew reporting grace. Stop intent commits before cleanup; a late successful start cannot return join credentials after intent. Status, control, signed Practice selection/replay and delayed-result release, and the authenticated sweep advance the same due-state decision; no serverless background timer is assumed. A correctly signed webhook cannot bypass a lease merely by being the first request after expiry. Sweep handles at most 100 attempts, oldest-reconciled first, and uses the configured provider transport for exact private-session cleanup.

## Exact resource reconciliation

Resource state is separate from call state: `not_dispatched`, `possible`, `known_running`, `stop_requested`, or `confirmed_stopped`. Unknown outcomes retain the user slot/account capacity until authoritative evidence exists. Elapsed time, a closed browser, call completion, DELETE acknowledgement, 404 or an empty listing cannot release the slot. No hard provider ceiling or billing amount is invented.

The transport has `start`, exact `read(sessionId)` and exact `stop(sessionId)`. The [Pipecat adapter](../../apps/workspace/src/sandbox/pipecat-transport.ts) uses independently supplied private service/deployment binding and private API authority for `GET`/`DELETE /v1/agents/{agentName}/sessions/{sessionId}`. It never substitutes public start credentials or operator/CLI authority, learns ownership from the first observed session, or uses the spike framework. Readback must match session, organization, service, deployment and configured agent before any stop or terminal conclusion.

Every observed session has a durable reconciliation lease and stop-attempt count. Cleanup reads freshly before each stop, permits at most three stops with 5- then 15-second spacing, and commits the count before sending. Lost stop responses consume their try. Forbidden or mismatched ownership blocks further mutations. Only matching terminal readback confirms termination. Slot release also waits for dispatch settlement and every observed session to be confirmed stopped. Resource proof does not establish billed duration; billing remains unknown.

### Pipecat transport contract

The adapter factory does no I/O and reads no environment or metadata. Construction requires distinct, explicitly supplied public/private credentials and independently verified organization UUID, service UUID (`deployment.serviceId`), deployment UUID and agent name. Organization namespace/slug is not the UUID. The adapter copies this binding, fixes the Pipecat API origin, disables redirects and automatic retries, bounds each HTTP operation to 15 seconds and streamed JSON to 256 KiB, and exposes only fixed failure categories. [provider.ts](../../apps/workspace/src/sandbox/provider.ts) constructs it when all five server settings are valid. Legacy Integration uses its unchanged existing adapter.

One public start POST requests Daily transport, room/token expiration at or before the lifecycle's committed absolute execution deadline, room/token ejection, non-owner token, initial video off and screensharing disabled. The runner body is exactly `{callId, apiBase, agentToken}`; bounds remain outside it. On a parseable response, the lifecycle callback commits the exact bounded session identity before HTTP/media post-validation. Invalid media, permission failure, interrupted/unknown start or a later contradictory no-start result cannot erase an observed cleanup target. Responses that never yield a complete bounded parse have no recoverable identity; authenticated runtime registration remains the only alternate application source. There is no guessed list/time matching.

The 15-second deadline bounds remote fetch/body work and media verification, not required database settlement. After observing an identity, `start` owns and awaits its retention even if HTTP is aborted; lifecycle signals the deadline without racing that transaction. Until retention settles, dispatch remains unsettled and the original admission slot stays held even when every earlier identity is terminal. A new durable reference reasserts unresolved resource state under the attempt lock, including after existing stop intent. Persistence failure leaves dispatch unsettled and denies join/release rather than dropping the identity uncertainty. This can outlive the HTTP budget during database contention or retain capacity after database failure; it cannot detach a late write, silently release capacity or re-reserve quota after release. Injected transports must honor the same ownership contract.

Documented invalid-request/authentication rejection (400/401), without any observed session, is definite no-start; locally rejected input sends no request. Other HTTP errors, malformed success, disconnect, abort and timeout are unknown. Exact private GET requires all four UUID fields to match the configured target and plausible creation/end timestamps. An explicit ended timestamp plus nonempty completion status establishes the adapter's terminal observation; metrics and billed amounts are not inferred. DELETE rechecks ownership through exact GET even for a direct caller, accepts only the matching documented acknowledgement, and never itself marks resources stopped. No default retry or public-key fallback exists.

**Browser-media verification limit:** the inspected public Pipecat response describes `dailyToken` only as access to the room. It does not establish a distinct browser-versus-agent token identity or a supported encoded-claim layout proving non-owner, exact-room or audio-only scope. Requesting properties is not proof that the returned token satisfies them. The server-owned [Practice verifier](../../apps/workspace/src/sandbox/browser-media.ts) therefore returns only an expiry: the token's decoded `exp` when available, clamped to the committed execution deadline, or the deadline for an opaque token. It rejects an already expired token and cannot extend a call. It does not claim token scope or verify a token signature. [ADR 015](../decisions/015-server-configured-sandbox-execution.md) records this operational choice; effective media scope and resource limits remain acceptance questions under #66.

Source inspection (public, unauthenticated, 2026-09-22): [Pipecat start](https://docs.pipecat.ai/api-reference/pipecat-cloud/rest-reference/endpoint/start), [official OpenAPI](https://docs.pipecat.ai/api-reference/pipecat-cloud/rest-reference/openapi.json), [Daily integration](https://docs.pipecat.ai/pipecat-cloud/guides/daily-webrtc), [Daily token scope/ejection](https://docs.daily.co/reference/rest-api/meeting-tokens), and [Daily room creation](https://docs.daily.co/reference/rest-api/rooms/create-room). The installed `pipecatcloud==0.4.4` start source corroborates the public start path/body passthrough but does not establish browser-token scope from the response. These source contracts do not replace live acceptance.

## Rollout and rollback

Apply additive migrations before the corresponding application code. Old Integration code ignores the Sandbox fields. Execution is enabled only by the five server provider settings, never a UI or per-request flag. To roll back live admission, remove or invalidate that server configuration first, retain handlers for existing attempts, and never drop additive records or clear unresolved slots to make the dashboard look finished. The [A07 evidence ledger](https://github.com/DevAnuhas/duplexd/issues/66) remains separate from this protocol description.
